1. Introducción

El presente documento corresponde al informe de la Iteración 2 del proyecto de desarrollo del sistema de información para el parqueadero Autos Colombia, desarrollado en el marco de la asignatura de Ingeniería de Software y Datos. Esta iteración se enfoca en la construcción y documentación de los módulos de Gestión de Usuarios y Gestión de Celdas, que complementan la Iteración 1 (gestión de entradas y salidas de vehículos).

El parqueadero Autos Colombia opera bajo un modelo de mensualidad fija, donde cada cliente registra uno o más vehículos y se le asigna una celda específica dentro de las instalaciones. El sistema web reemplaza los registros manuales en papel, brindando control en tiempo real del flujo vehicular, la ocupación del parqueadero y el estado de cartera de cada cliente. La solución está desarrollada sobre el stack Python + Flask + SQLAlchemy + Bootstrap 5, siguiendo el patrón de arquitectura MVC.

Contexto del Proyecto

El sistema se desarrolla en tres iteraciones. La primera iteración cubrió el registro de entradas y salidas de vehículos, la gestión de pagos, novedades y el dashboard de métricas. Esta segunda iteración profundiza en la gestión integral de usuarios (clientes del servicio) y de las celdas (espacios físicos del parqueadero), incluyendo todos los artefactos de análisis, diseño y pruebas que evidencian un desarrollo de software estructurado y de calidad.

Objetivos de la Iteración 2

  • Definir y documentar los requerimientos funcionales y no funcionales para la gestión de usuarios y celdas.
  • Elaborar los diagramas UML de casos de uso, secuencia y componentes correspondientes.

  • Establecer un plan de pruebas resumido con casos de prueba trazables a los requerimientos.
  • Actualizar el repositorio GitHub con el código fuente y la documentación generada.

2. Entregables

2.1 Requerimientos Funcionales — Gestión de Usuarios

RF-10 Registrar Usuario
Descripción: El sistema debe permitir registrar un nuevo cliente que contrata el servicio de mensualidad.
Actor: Administrador
Flujo principal:
  1. El administrador accede al módulo de Usuarios.
  2. Selecciona la opción "Nuevo Usuario".
  3. Ingresa: nombre completo, número de documento, teléfono, correo y dirección.
  4. El sistema valida que el documento y el correo no estén registrados previamente.
  5. El sistema guarda el usuario con estado activo y fecha de creación automática.
Postcondición: El usuario queda registrado con estado activo.
Flujo alternativo A: Si el documento ya existe → "El número de documento ya se encuentra registrado."
Flujo alternativo B: Si el correo ya existe → "El correo electrónico ya se encuentra registrado."
Restricciones: Nombre (3–100 car.), Documento (solo dígitos, 6–15), Correo (formato válido), Teléfono (máx. 15 dígitos).
RF-11 Consultar y Buscar Usuarios
Descripción: El sistema debe permitir consultar el listado de usuarios con búsqueda por nombre, documento o correo, y paginación.
Actor: Administrador
Funcionalidades: Lista paginada de usuarios activos · Filtro en tiempo real · Ordenamiento ascendente por nombre.
Regla de negocio: Los usuarios inactivos no aparecen en el listado principal.
RF-12 Ver Perfil Detallado de Usuario
Descripción: El sistema debe mostrar el perfil completo de un usuario con sus vehículos y pagos asociados.
Actor: Administrador
Información mostrada: Datos personales · Estado y fecha de registro · Vehículos (placa, marca/modelo, celda) · Últimos pagos (período, monto, método).
RF-13 Editar Información de Usuario
Descripción: El sistema debe permitir actualizar los datos de un usuario existente.
Actor: Administrador
Campos editables: Nombre completo · Teléfono · Correo electrónico · Dirección.
Restricción: El número de documento no puede ser modificado una vez registrado.
RF-14 Desactivar Usuario
Descripción: El sistema debe permitir desactivar a un usuario sin eliminarlo físicamente de la base de datos.
Actor: Administrador
Flujo principal: El administrador accede al perfil → selecciona "Desactivar" → confirma → el usuario pasa a estado inactivo.
Flujo alternativo: Si el usuario tiene vehículos activos, el sistema muestra advertencia.
Regla de negocio: El historial se conserva íntegro. Los usuarios desactivados pueden ser reactivados.

2.2 Requerimientos Funcionales — Gestión de Celdas

RF-15 Crear Celda
Descripción: El sistema debe permitir registrar una nueva celda de parqueadero.
Actor: Administrador
Datos requeridos: Número de celda (único) · Tipo de vehículo (carro/moto/camión) · Piso · Tarifa mensual (COP).
Postcondición: La celda queda con estado "disponible" por defecto.
Flujo alternativo: Si el número ya existe → "El número de celda ya está registrado."
RF-16 Editar Información de Celda
Descripción: El sistema debe permitir actualizar los datos de una celda existente.
Campos editables: Tipo de vehículo · Piso · Tarifa mensual.
Restricción: El número de celda no puede ser modificado una vez creado.
Regla de negocio: Si la celda está ocupada, el cambio de tarifa aplica desde el siguiente período.
RF-17 Consultar y Filtrar Celdas
Descripción: El sistema debe permitir consultar todas las celdas en vista de cuadrícula con filtros.
Actor: Administrador / Operador
Funcionalidades: Vista grid · Color verde = disponible · Color amarillo = ocupada · Filtros por tipo, estado y piso · Estadísticas de ocupación en la parte superior.
RF-18 Ver Estadísticas de Ocupación
Descripción: El sistema debe presentar métricas de ocupación de celdas en tiempo real.
Indicadores: Total de celdas · Disponibles (total y %) · Ocupadas (total y %) · Desglose por tipo · Capacidad por piso.

2.3 Requerimientos No Funcionales

ID Nombre Descripción
RNF-09 Rendimiento El listado de usuarios carga en <1.5 s con 500 usuarios. El panel de celdas renderiza en <1 s con 200 celdas.
RNF-10 Usabilidad Formularios completables en <2 min. Mensajes de validación claros junto al campo con error. Campos obligatorios marcados visualmente con asterisco.
RNF-11 Integridad Usuarios No pueden existir dos usuarios con el mismo documento ni correo. La eliminación es lógica (cambio de estado), nunca física. Historial preservado íntegramente.
RNF-12 Integridad Celdas No puede haber celdas con número duplicado. Una celda ocupada no puede asignarse a otro vehículo sin liberarla primero. El estado se actualiza automáticamente.
RNF-13 Consistencia Visual Celdas disponibles: verde #198754. Celdas ocupadas: amarillo #ffc107. Vista responsiva desde 768px.
RNF-14 Trazabilidad El sistema registra fecha de creación de cada usuario. Los cambios de estado de celda son rastreables vía movimientos/vehículos.
RNF-15 Accesibilidad Etiquetas label correctamente asociadas a campos. Contraste de colores cumple nivel AA de las WCAG 2.1.

Módulo: Gestión de Usuarios

HU-10 Buscar y Consultar Usuarios
Alta
2 puntos
Como administrador del parqueadero,
quiero buscar usuarios por nombre, documento o correo,
para encontrar rápidamente el perfil de un cliente sin recorrer toda la lista.
Criterios de Aceptación:
  • El sistema muestra una lista paginada de todos los usuarios activos al ingresar al módulo.
  • El campo de búsqueda filtra en tiempo real por nombre completo, documento o correo.
  • Cada fila muestra: nombre, documento, correo, teléfono y estado.
  • Si no hay resultados: "No se encontraron usuarios con ese criterio."
  • La lista soporta hasta 500 usuarios sin exceder 1.5 s de carga.
HU-11 Ver Perfil Detallado de Usuario
Alta
2 puntos
Como administrador del parqueadero,
quiero ver toda la información de un cliente en una sola pantalla,
para conocer sus vehículos, celdas asignadas e historial de pagos sin navegar por múltiples módulos.
Criterios de Aceptación:
  • El perfil muestra: nombre, documento, correo, teléfono, dirección, estado y fecha de registro.
  • Muestra la lista de vehículos con placa, marca/modelo, tipo y celda asignada.
  • Muestra los últimos 5 pagos con período, monto y método de pago.
  • Desde el perfil hay botones directos: "Editar" y "Desactivar".
HU-12 Editar Información de Usuario
Alta
2 puntos
Como administrador del parqueadero,
quiero actualizar los datos de contacto de un cliente,
para mantener la información del sistema al día ante cambios de teléfono, correo o dirección.
Criterios de Aceptación:
  • El formulario viene pre-cargado con los datos actuales del usuario.
  • Campos editables: nombre completo, teléfono, correo y dirección.
  • El número de documento aparece como campo de solo lectura (readonly).
  • El sistema valida que el correo nuevo no esté en uso por otro usuario.
  • Al guardar: "Usuario actualizado correctamente."
HU-13 Desactivar Usuario
Alta
3 puntos
Como administrador del parqueadero,
quiero desactivar a un cliente que ya no usa el servicio,
para retirar sus accesos sin perder el historial histórico de pagos y vehículos.
Criterios de Aceptación:
  • La opción "Desactivar" está disponible en el perfil del usuario activo.
  • El sistema solicita confirmación antes de ejecutar la acción.
  • Al confirmar, el usuario pasa a inactivo y desaparece del listado principal.
  • Los vehículos, pagos y movimientos asociados se conservan íntegramente.
  • Si tiene vehículos activos, muestra advertencia antes de proceder.
  • Un usuario inactivo puede ser reactivado desde su perfil.

Módulo: Gestión de Celdas

HU-14 Crear Nueva Celda
Alta
2 puntos
Como administrador del parqueadero,
quiero registrar una nueva celda en el sistema,
para habilitar nuevos espacios cuando el parqueadero amplíe su capacidad.
Criterios de Aceptación:
  • El formulario solicita: número de celda, tipo (carro/moto/camión), piso y tarifa mensual.
  • El número de celda debe ser único en el sistema.
  • Al crear, el estado inicial es "disponible" automáticamente.
  • La tarifa debe ser un valor positivo mayor a cero en COP.
  • Al guardar: "Celda creada exitosamente."
HU-15 Editar Celda
Media
2 puntos
Como administrador del parqueadero,
quiero actualizar los datos de una celda existente,
para corregir errores de registro o ajustar las tarifas mensuales.
Criterios de Aceptación:
  • El formulario viene pre-cargado con los datos actuales de la celda.
  • Campos editables: tipo de vehículo, piso y tarifa mensual.
  • El número de celda aparece como campo de solo lectura (readonly).
  • Al guardar: "Celda actualizada correctamente."
HU-16 Visualizar y Filtrar Celdas
Alta
2 puntos
Como operador del parqueadero,
quiero ver el estado de todas las celdas en un panel visual con filtros,
para identificar rápidamente cuáles están disponibles y asignarlas a nuevos clientes.
Criterios de Aceptación:
  • El sistema muestra todas las celdas en formato de cuadrícula (grid card).
  • Celdas disponibles: fondo verde · Celdas ocupadas: fondo amarillo.
  • Cada tarjeta muestra: número, ícono del tipo, piso y tarifa mensual.
  • Filtros simultáneos por: tipo, estado y piso.
  • Estadísticas en la parte superior: Total, Disponibles y Ocupadas.
HU-17 Asignar Celda Disponible a Vehículo
Alta
3 puntos
Como administrador del parqueadero,
quiero que al registrar un vehículo solo se puedan seleccionar celdas disponibles del tipo correcto,
para evitar asignaciones incorrectas y garantizar que cada celda tenga máximo un vehículo.
Criterios de Aceptación:
  • El selector de celdas muestra únicamente celdas con estado "disponible".
  • Al guardar el vehículo, la celda asignada cambia automáticamente a "ocupada".
  • Si no hay celdas disponibles del tipo requerido: "No hay celdas disponibles para este tipo de vehículo."
  • Al desactivar un vehículo, la celda vuelve automáticamente a "disponible".

3. Conclusiones

1

La Iteración 2 del sistema Parqueadero Autos Colombia consolidó la gestión integral de los dos activos fundamentales del negocio: los usuarios (clientes con contrato de mensualidad) y las celdas (espacios físicos del parqueadero). La implementación de operaciones CRUD completas para ambos módulos, con validaciones de integridad a nivel de base de datos y de capa de negocio, garantiza la consistencia y confiabilidad de la información operativa.

2

La definición de 9 requerimientos funcionales (RF-10 a RF-18) y 7 requerimientos no funcionales (RNF-09 a RNF-15) proporcionó una base sólida y trazable para el desarrollo. Cada funcionalidad implementada puede rastrearse desde la historia de usuario hasta el caso de prueba correspondiente, lo que demuestra una práctica de ingeniería de software disciplinada y orientada a la calidad.

3

Los diagramas UML elaborados (casos de uso, secuencia y componentes) aportaron una visión clara de la arquitectura del sistema y los flujos de interacción. El diagrama de componentes en particular evidencia la correcta separación de responsabilidades entre las capas de presentación, control, modelo y datos, siguiendo el patrón MVC que facilita el mantenimiento y la escalabilidad futura del sistema.

4

Las 8 historias de usuario (HU-10 a HU-17, totalizando 18 puntos de historia) con criterios de aceptación verificables facilitaron la comunicación entre el equipo técnico y los requerimientos del negocio. El acumulado del proyecto alcanza 40 puntos de historia en 17 historias entre las dos iteraciones, reflejando un alcance bien dimensionado para el contexto operativo del parqueadero.

5

El plan de pruebas con 20 casos de prueba organizados por módulo, incluyendo flujos positivos y negativos, y la matriz de trazabilidad RF–HU–RNF, constituyen una herramienta práctica para validar la calidad del software antes de su entrega. El enfoque de eliminación lógica (soft delete) para usuarios, combinado con la actualización automática de estado de celdas al registrar vehículos, garantiza la integridad referencial y la trazabilidad histórica de todas las operaciones.

6

El versionamiento en GitHub y la documentación técnica estructurada en la carpeta /docs del repositorio evidencian buenas prácticas de desarrollo colaborativo y gestión del conocimiento. La arquitectura del sistema, basada en Flask con Blueprints, SQLAlchemy y SQLite (migrable a PostgreSQL), garantiza portabilidad y escalabilidad para futuras iteraciones del proyecto.
